# 32. Identified Multivalued Metadata Items

Date: 2026-07-02

## Status

Accepted

Extends [31. AI Provenance](0031-ai-provenance.md)

## Context

Meadow's repeating free-text descriptive fields (`description`, `keywords`,
`abstract`, and twenty-one others) have always been stored as bare string
arrays. A string array gives its items no identity: "the second description"
is only meaningful until someone edits, reorders, or re-imports the list.

[ADR 31](0031-ai-provenance.md) made that a correctness problem. Item-level AI
provenance must be able to say *this specific item* was AI-generated, *that
one* was human-edited after an AI proposal, and *the other* is purely human,
and those claims must survive ordinary editing. With value-as-identity, any
attribution scheme is forced to reconstruct correspondence after the fact, and
every reconstruction heuristic fails in ordinary cases:

- **Positional matching fabricates lineage.** Pairing "leftover" current items
  against dropped proposed items by position labels a purely human addition as
  an edit of a deleted AI item whenever a user deletes one item and adds
  another in the same save. For a provenance system, a fabricated claim is the
  single unacceptable failure mode.
- **Value matching loses lineage on every edit.** The moment a human fixes a
  typo in an AI-generated value, the value-keyed identity is destroyed and the
  item's history detaches, including any explicit human attestation recorded
  against it.
- **Duplicate values collapse.** Two identical keywords are one identity.

The failure was structural, not a matter of tuning: identity recovered from
content cannot survive changes to that content. Meanwhile the codebase already
had the answer in its other repeating fields: notes, related URLs, and
controlled entries are Ecto embeds, and controlled entries carry a stable
natural key (their authority `term.id`). Free-text strings were the odd ones
out.

Two constraints shaped the solution. First, several write paths bypass Ecto
changesets entirely and write jsonb directly (CSV metadata update jobs via
`COPY`/`UPDATE`, batch updates via set-based SQL); identity has to survive
those too, or bulk operations would silently sever provenance at scale.
Second, the flattened string representation is public surface (the search
index feeds the DC API, and CSV export is hand-edited by staff), so identity
had to be introduced without breaking either shape.

## Decision

Store each repeating free-text value as an identified `ValueEntry` embed
(`{id, value}`, binary id, autogenerated), and give notes and
related URLs autogenerated ids as well. A one-time migration rewrites existing
jsonb (minting ids for every item) and stamps the new ids onto existing AI
provenance records, matching stored items to live items by natural key and
pairing at most one unmatched item per field as an in-place edit; anything
more ambiguous is never guessed. If an applied provenance target cannot be
fully stamped, the migration fails and the shared transaction leaves both the
work rewrite and provenance unchanged. Meadow can stop writes for this
forward-only cutover, so correctness takes priority over online migration or
rollback machinery.

On top of the embeds, adopt a single **identity contract**, implemented once
in `Meadow.Data.ItemIdentity` and honored by every write path:

> An item that echoes its stable `id` keeps that identity only when the id
> belongs to the same field on the same work. An id-less item keeps its
> identity when its content exactly matches a current item's natural key, each
> existing id claimed at most once, in list order. Anything else is new content
> and gets a fresh server-minted id. Malformed, duplicate, or foreign ids are
> rejected. **No path ever infers correspondence by position or fuzzy
> similarity.**

The contract's failure direction is deliberate: when a match cannot be made,
the item reads as new content and simply carries no AI lineage. Provenance can
be *dropped* by an id-less edit, but never *fabricated*, and the append-only
event log (ADR 31) still holds the full history.

Each boundary applies the contract in its own dialect:

- **Changeset writes** (work form, GraphQL, CSV-derived updates): params are
  normalized (bare strings become entry params) and rehydrated against the
  field's current entries before `cast_embed`, so re-sending an unchanged list
  is a no-op for identity even from id-less callers.
- **Direct-jsonb writes** must produce well-formed identified items:
  `WorkDescriptiveMetadata.jsonb_value_entries/1` normalizes and mints at each
  such boundary (planner apply, batch merge, bulk import), and rejects malformed
  or duplicate supplied ids.
- **AI plan changes** mint ids at the plan-change boundary
  (`Planner.normalize_value_entry_operations/1`), so the AI's proposed item and
  the eventually applied work item share one id from birth. At apply time the
  operations are reconciled against the destination work
  (`ItemIdentity.reconcile_proposed/4` for replaces,
  `ItemIdentity.reconcile_appended/3` for adds, with the work row locked): a
  value the work already holds keeps its existing id (and its per-item lineage,
  including human attestations), a genuinely new value keeps its minted id, and
  an id that is provably foreign (owned by another identified field of the same
  work), duplicated, or malformed fails the apply instead of being written. A
  minted id that cannot be proven foreign is kept by design: it entered at the
  plan-change boundary, and rejecting it would orphan new content. The one
  residual is a UUID copied from a different work attached to new content,
  which is stored verbatim; the caller already holds edit rights to both works,
  and per-item attribution is scoped per work, so no lineage can leak.
- **CSV round-trips ids in the cell**: export writes each item as `uuid:value`
  (the same `prefix:content` cell convention as `GENERAL_NOTE:text`; the pipe
  remains the between-items separator), and import recognizes the strict
  36-character UUID prefix, so free text containing colons cannot be misparsed.
  Because the search index deliberately flattens these fields (public DC API
  shape), export overlays the identified entries from Postgres one scroll
  chunk at a time rather than indexing the ids. Hand-authored id-less cells
  fall back to exact-value rehydration at import time. A prefixed id is accepted
  only when it already belongs to that field on that work.
- **Batch updates** handle identified fields *per work*. Appends discard any
  supplied ids and mint a distinct id for every appended item on every work.
  Replaces reconcile ids against each destination field, rejecting copied or
  duplicate ids before updating. The OpenSearch query only selects; identity
  is resolved from current Postgres jsonb while the work row is locked.
- **GraphQL**: output is a `ValueEntry` scalar serializing `{id, value}` (a
  scalar needs no subselection, so existing query documents are unchanged);
  input is a typed `value_entry_input` object, so a malformed item is a
  validation error rather than a silently dropped id. The editor UI
  round-trips ids explicitly (hidden inputs; `react-hook-form` is configured
  with a non-default key name so its internal row key cannot clobber the
  stable id).
- **Public boundaries stay flat**: the search index and the DC API continue to
  see plain strings (`ValueEntry.values/1`), and the AI agent is shown
  flattened values so it proposes free-text replaces rather than
  controlled-style operations.

Controlled entries deliberately do **not** gain a synthetic embed id: their
authority `term.id` is already a stable natural key, and per-item provenance
keys controlled items on it.

## Consequences

Per-item AI attribution becomes an exact id lookup instead of a
reconstruction: it survives in-place edits, reordering, duplicate values, CSV
round-trips, batch replaces, and applied plan changes (including a plan that
re-proposes values the work already holds), and per-item human attestations
stay attached to the item they attest. The plan-diff view still matches proposed items to
current items by *value*, deliberately: a proposal's items are minted
fresh ids at the plan boundary, so id equality cannot pair them; duplicate
values therefore collapse in that display (a cosmetic nuance, never a wrong
attribution).

Identity is now an invariant every write path must uphold. An id is owned by
one item in one field on one work; it is not a portable content identifier. A
new direct-jsonb write path that forgets to normalize will store malformed
entries that fail loudly at embed-load time; a client that round-trips values
without echoing ids will remint edited values and detach their per-item
provenance.
The changeset-level exact-value rehydration protects unchanged values from
id-less callers, but an *edited* value without its id is, by design, new
content: clients that want in-place-edit identity must echo the id (the
Meadow editor does; CSV export makes it automatic for staff).

Bulk operations pay a modest, bounded cost: CSV export adds one database read
per scroll chunk (which also fixed a pre-existing data-loss bug: fields
absent from the search index, such as `citation`, previously exported as
empty cells and were erased on re-import). Identified batch updates perform
one locked update per work so validation and id minting are scoped to the
destination work. That cost is acceptable for a staff-facing system and keeps
the ownership invariant simple enough to audit.

The CSV cell format for these fields changes from `value` to `uuid:value`.
Staff already handle prefixed cells for notes and related URLs; sheets built
by hand without ids remain valid and lose nothing for unchanged values.

Finally, the identity rule itself lives in one module (`ItemIdentity`), shared
verbatim by the changeset, the CSV bulk import, and batch replace. Any future
write path should reuse it rather than approximate it: the alternative,
inferring identity after the fact, is exactly the failure this decision
exists to remove.
